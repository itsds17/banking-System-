# Real-Time Banking Decision Intelligence & Risk Analytics Platform

> **A production-style end-to-end Data Science + Data Engineering + MLOps portfolio project built to demonstrate Barclays Data Scientist-level skills.**

---

## Project Overview

This platform simulates a real-time banking risk intelligence system. It ingests simulated transaction streams, applies machine-learning fraud and credit-risk models, enriches decisions with device/IP/graph intelligence, and surfaces actionable decisions through a FastAPI service and Streamlit dashboard — all running locally without any cloud dependencies.

**Business problem:** Banks process millions of transactions daily. Fraudulent transactions cost the global banking industry billions annually. At the same time, poor lending decisions increase default rates and capital risk. This platform demonstrates how modern Data Science + MLOps can automate, explain, and continuously improve these decisions.

## Fraud Scenarios

Fraud labels are **not randomly assigned**. The generator injects 13 correlated fraud patterns:

| # | Scenario | Description |
|---|---|---|
| 1 | New Device Fraud | Transaction from a device the customer has never used |
| 2 | Velocity Attack | 3+ transactions in under 60 seconds |
| 3 | Impossible Travel | Two transactions in cities 900+ km apart within 30 minutes |
| 4 | Unusual Hours | Large transactions at 2–4 AM |
| 5 | Merchant Collusion | High-risk merchant + amount 3× customer average |
| 6 | Account Takeover | New device + amount 5× customer average |
| 7 | Device Sharing | Device used by more than 3 different customers |
| 8 | IP Sharing | IP used by more than 5 different customers |
| 9 | Coordinated Network | Cluster of customers routing funds to the same target |
| 10 | Abnormal Spending | Transaction amount > 5 standard deviations from customer mean |
| 11 | Repeated Failures | 4+ attempts in 5 minutes before success |
| 12 | Card Not Present | Online gambling/crypto transaction with no prior online history |
| 13 | Geo Anomaly | Transaction 3,000+ km from customer home city |

## Device Intelligence

Each transaction carries a `device_id` (SHA-256 fingerprint — simulating what a real bank's upstream API would capture automatically). The system:

- Maintains a `customer_devices` relationship table
- Detects whether each transaction uses a **known** or **new** device
- Tracks per-device: customer count, transaction count, fraud count, age
- Creates `device_risk_score` for use in the Decision Engine

**IMPORTANT**: This is a simulation. No real device detection occurs. The transaction simulator provides device information automatically — the user does not enter device IDs manually.

---

## IP Intelligence

`ip_address` is tracked separately from `device_id` as an independent signal:

- Each customer has a pool of known IPs (home, work, mobile)
- A fraction of IPs are shared across multiple customers (fraud signal)
- Features: `new_ip`, `ip_customer_count`, `ip_fraud_count`, `ip_risk_score`

## PySpark Processing (Phase 3)

PySpark is used for **large-scale batch feature engineering** — specifically for operations that need to run across millions of transactions efficiently:

- Window functions for transaction velocity (1-min, 5-min, 1-hour rolling counts)
- Customer-level behavioural aggregates (mean, stddev, percentiles)
- Device and IP-level aggregates across the full transaction history
- Merchant risk enrichment at scale

**Why PySpark instead of pandas?** At 500k–2M transactions, pandas is slow for multi-table window joins. PySpark runs these on a distributed execution plan, processing partitions in parallel — and scales to production-sized datasets by adding executors.

## Credit Risk Model (Phase 5)

Predicts **Probability of Default (PD)** on loans.

**Expected Loss formula:**
```
Expected Loss = PD × LGD × EAD

PD  = Probability of Default (predicted by XGBoost)
LGD = Loss Given Default (industry assumption: ~45%)
EAD = Exposure at Default (outstanding loan balance)
```

---

## Decision Engine (Phase 10)

Combines all signals into a single risk decision:

```
risk_score = w₁×fraud_score + w₂×credit_risk + w₃×device_risk + w₄×ip_risk + w₅×graph_risk

Decision:
  ≥ 0.80 → BLOCK
  ≥ 0.40 → REVIEW (with reason codes)
  < 0.40 → APPROVE
```

Reason codes explain every REVIEW/BLOCK decision to satisfy Explainable AI requirements.

## How to Run

### Prerequisites
- Python 3.9+
- Java 17 (for PySpark)
- Docker Desktop

### Quick Start

```powershell
# 1. Clone the repository
git clone https://github.com/itsds17/banking-System-.git
cd banking-System-

# 2. Create virtual environment and install dependencies
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# 3. Copy environment variables
copy .env.example .env

# 4. Generate synthetic data (default: 10k customers, 500k transactions)
python scripts/generate_data.py

# 5. Start Docker services (PostgreSQL, Kafka, MLflow)
docker compose up -d

# 6. Run all tests
pytest tests/ -v

# 7. Access services
# MLflow UI:  http://localhost:5000
# FastAPI:    http://localhost:8000/docs
# Streamlit:  http://localhost:8501
```

### Generate a small test dataset (CI-safe)
```powershell
python scripts/generate_data.py --customers 1000 --transactions 50000
```

### Generate a large dataset (requires 16+ GB RAM)
```powershell
python scripts/generate_data.py --customers 50000 --transactions 2000000
```

## Limitations

- All data is synthetic — patterns are realistic but not derived from real banking data.
- NetworkX is used for graph analytics (not a production-scale graph database like Neo4j).
- PySpark runs in local mode (not a cluster) — suitable for demonstrating distributed logic.
- Kafka runs as a single broker (not multi-broker HA) — appropriate for local portfolio use.
